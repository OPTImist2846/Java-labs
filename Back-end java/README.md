# FPV Fleet

Back-end розробка на Java. Система обліку FPV-пілотів, їхніх дронів,
обладнання та журналів польотів.

## Запуск

Потрібні MySQL на `localhost:3306` (`root` / `root`) і Docker.

```
docker compose up -d
./mvnw spring-boot:run
```

Застосунок: http://localhost:8080, Keycloak: http://localhost:8081.
Користувачі Keycloak: `admin/admin` (ADMIN, PILOT), `pilot/pilot` (PILOT), `viewer/viewer` (без ролей).

## Лабораторна робота №1. Spring Security

**Завдання:** закласти фундамент системи: предметна область, базовий CRUD, база даних під контролем
міграцій, простий UI та подвійна автентифікація (OIDC для UI і JWT для API).

**Предметна область.** Облік FPV-пілотів (`Pilot`), їхніх дронів (`Drone`), обладнання (`Equipment`)
і журналів польотів (`FlightLog`). Область легко розширюється надалі: обслуговування дронів,
статистика польотів, навчання пілотів.

### Виконання критеріїв

**AC1. CRUD.** Для всіх сутностей зроблено Controller, Service, Repository, Entity і DTO, мапінг
через MapStruct. REST API: `/api/v1/pilots`, `/api/v1/drones`, `/api/v1/equipment`,
`/api/v1/flight-logs` з операціями GET, POST, PUT, DELETE.

**AC2. Міграції.** Схему створює Liquibase (`src/main/resources/db/changelog`), Hibernate працює
в режимі `validate`.

**AC3. UI.** Сторінки на Thymeleaf за адресою `/ui` дозволяють переглядати, створювати,
редагувати й видаляти записи.

**AC4. OIDC.** При відкритті `/ui` користувача перенаправляє на логін Keycloak, після входу він
повертається в застосунок із сесією. Realm імпортується автоматично з `keycloak/fpv-fleet-realm.json`.

**AC5. JWT.** Запити до `/api/**` обробляє окремий `SecurityFilterChain` без сесії, автентифікація
через заголовок `Authorization: Bearer <token>`.

**AC6. SecurityFilterChain.** DELETE-запити до API і зміна пілотів дозволені лише ролі `ADMIN`,
інакше 403.

**AC7. @PreAuthorize.** Методи сервісів перевіряють ролі незалежно від фільтрів. Наприклад,
`viewer` проходить фільтр як автентифікований, але при читанні дронів отримує 403.

**AC8. Колекція запитів.** Файл `http/fpv-fleet.http` для IntelliJ HTTP Client отримує токени,
проходить повний CRUD і перевіряє відповіді 401, 403 та 404.

### Висновок

Створено основу проєкту на Spring Boot з CRUD, міграціями Liquibase та простим UI. Налаштовано
автентифікацію через Keycloak двома способами (OIDC і JWT) та обмеження доступу на рівні
`SecurityFilterChain` і `@PreAuthorize`.

## Лабораторна робота №2. Unit-тестування

**Завдання:** покрити існуючий код unit-тестами щонайменше на 60%, щоб переконатися, що бізнес-логіка
поводиться так, як задумано, і виявити проблеми в коді.

**Запуск тестів:** `./mvnw verify`. Звіт покриття JaCoCo з'являється в `target/site/jacoco/index.html`,
збірка падає, якщо покриття рядків нижче 60%.

**Результат:** 129 тестів, усі проходять. Покриття рядків 87.8%, інструкцій 89%.

### Виконання критеріїв

**AC1. Звичайні сценарії.** Кожен тест перевіряє реальний результат: поля повернутого DTO, стан
зміненої сутності, HTTP-статус і тіло відповіді, а не лише відсутність винятку.

**AC2. Невалідні дані та граничні значення.** Окремі тести перевіряють неіснуючі ID, відсутній `pilotId`,
дублікати username та email, тривалість польоту `null`, 0 і від'ємну (а 1 хвилина приймається),
порожнє середовище та відсутню дату польоту.

**AC3. Моки.** Залежності замінено через `@Mock` / `@InjectMocks` з `MockitoExtension`. Мапери
підключені як `@Spy` справжньої реалізації MapStruct. Spring-контекст не запускається.

**AC4. Перевірка, що тести ловлять помилки.** Логіку двічі навмисно зламано (див. `docs/lab2`):
у `FlightLogService` умову `<= 0` замінено на `< 0`, а в `PilotService.updatePilot` прибрано `!`
у перевірці унікальності username. В обох випадках відповідні тести впали, після повернення коду
знову пройшли.

**AC5. Ізоляція.** Тести не звертаються до БД, мережі чи файлів, не залежать від порядку і не
використовують `Thread.sleep`. Час у UI-контролері береться з `Clock`, у тестах він фіксований.
Тест `contextLoads`, який потребував MySQL і Keycloak, видалено.

**AC6. Іменування та структура.** Імена мають вигляд `метод_сценарій_очікуванийРезультат`,
наприклад `createLog_nonPositiveDuration_throwsAndDoesNotSave`. Тіло поділено на блоки
Arrange, Act, Assert, для моків використано BDD-стиль `given(...)` / `then(...).should()`.

**AC7. Побічні ефекти.** Виклики `save` і `delete` перевіряються через `then(...).should()` та
`ArgumentCaptor` з перевіркою переданих значень, а в сценаріях помилок перевіряється, що
`save` чи `delete` не викликались.

**AC8. Усі публічні методи.** Для кожного публічного методу `PilotService`, `DroneService`,
`EquipmentService` і `FlightLogService` є і звичайний тест, і тест на помилку або граничне значення.

### Знайдені проблеми

Під час написання тестів у коді виявлено й виправлено чотири проблеми:

1. Сутності з `@Data` і двосторонніми зв'язками мали рекурсивні `equals` / `hashCode`, що призводило
   до `StackOverflowError`. Замінено на `@Getter` / `@Setter`.
2. `PilotService` не перевіряв унікальність email, дублікат падав у базі з помилкою 409.
3. `FlightLogService` приймав нульову чи від'ємну тривалість, порожнє середовище та відсутню дату.
4. `FlightLogUiController` брав поточний час напряму, що робило його нетестованим. Додано `Clock`.

### Висновок

Існуючий код покрито unit-тестами на JUnit 5, Mockito та AssertJ з покриттям 87.8%. Тести
перевіряють як звичайні сценарії, так і обробку помилок, працюють без Spring-контексту і реально
ловлять зламану логіку. Під час тестування знайдено та виправлено чотири дефекти.

## Лабораторна робота №3. Map, Set, Generics, Wildcards

**Завдання:** вісім вправ на колекції `Map` і `Set`, generic-класи та методи, а також upper- і
lower-bounded wildcards.

Код знаходиться в пакеті `com.example.fpvfleet.lab3`, по одному підпакету на тему. Усі завдання
демонструє клас `Lab3Demo`: його можна запустити в IntelliJ або командою

```
./mvnw compile
java -cp target/classes com.example.fpvfleet.lab3.Lab3Demo
```

### Виконання завдань

**1. Реєстр студентів.** `Student` є record з номером залікової книжки, ім'ям, прізвищем, групою та
середнім балом. `StudentRegistry` зберігає студентів у `LinkedHashMap` за номером залікової, тому
пошук за ID працює швидко, а список виводиться в порядку додавання. Є методи додавання (дублікат
номера не перезаписує існуючого студента), видалення, пошуку за ID, прізвищем і групою та виведення
всіх студентів.

**2. Унікальні елементи.** `UniqueElements.unique` повертає `LinkedHashSet`, тобто прибирає дублікати
і зберігає порядок першої появи. `countOccurrences` повертає `Map` з кількістю входжень кожного
елемента.

**3. Box&lt;T&gt;.** Ящик з необов'язковою місткістю: `put` кладе предмет, `take` дістає перший
покладений і повертає `Optional`. Перевірено з `String`, `Integer`, `Student` та `List<Double>`.

**4. findMax.** Сигнатура `<T extends Comparable<? super T>> T findMax(T[] array)`. Перевірено з
`Integer`, `Double`, `Character`, `String`, а також з `LocalDate`, який реалізує `Comparable` через
батьківський інтерфейс. Порожній масив або `null` в елементах дають `IllegalArgumentException`.

**5. Pair&lt;F, S&gt;.** Пара двох значень будь-яких типів, наприклад `Pair<Integer, String>` і
`Pair<String, List<Integer>>`. Метод `isSameAs` порівнює дві пари за вмістом, а `compare` впорядковує
пари, якщо обидва компоненти порівнювані.

**6. Upper-bounded wildcard.** Абстрактний `Shape` з `getArea()`, підкласи `Circle` і `Rectangle`.
`ShapeCalculator.calculateTotalArea(List<? extends Shape>)` приймає `List<Shape>`, `List<Circle>`
і `List<Rectangle>`.

**7. Lower-bounded wildcard.** `IntegerLists.addToList(List<? super Integer>)` додає числа від 1 до 10
і працює з `List<Integer>`, `List<Number>` та `List<Object>`.

**8. Притулок для тварин.** Ієрархія `Animal`, `Dog`, `Cat` і `Labrador extends Dog`. `AnimalShelter`
тримає окремі списки собак та інших тварин. `addAnimals(List<? super Dog>, Collection<? extends Dog>)`
поєднує обидва види wildcard, тому до списку собак можна додати й `Labrador`. `printAnimalSounds`
проходить по `List<? extends Animal>` і виводить звук кожної тварини.

### Тестування

Кожне завдання покрито unit-тестами за правилами лабораторної №2, разом 85 тестів для lab3.
Тести перевіряють і звичайні сценарії, і помилкові дані. Покриття коду lab3 становить 99%,
загальне покриття проєкту 92%.

### Висновок

На практичних прикладах реалізовано роботу з `Map` і `Set`, generic-класи та методи з обмеженнями
типів, а також показано різницю між `? extends` (читання з колекції підтипів) і `? super`
(запис у колекцію супертипів).
