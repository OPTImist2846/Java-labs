# FPV Fleet

Семестровий проєкт з back-end розробки на Java. Це система обліку FPV-пілотів, їхніх дронів,
обладнання та журналів польотів. Кожна наступна лабораторна робота нарощує функціональність
на основі попередньої.

## Зміст

1. [Лабораторна робота №1. Spring Security (OIDC + JWT)](#лабораторна-робота-1)

## Предметна область

Система призначена для команди або школи FPV-пілотування. Вона веде облік пілотів, парку дронів,
персонального обладнання (окуляри, апаратура, акумулятори) та виконаних польотів.

Предметну область обрано з розрахунком на подальший розвиток у багатомодульну систему. Надалі
до неї можна додати облік обслуговування й ремонтів дронів, статистику налітаних годин,
модуль навчання з інструкторами та допусками, а також імпорт телеметрії.

Зараз модель складається з чотирьох сутностей. `Pilot` має username, email і роль у команді.
До пілота належать його дрони (`Drone`: назва та розмір рами), обладнання (`Equipment`: назва та тип)
і журнали польотів (`FlightLog`: середовище, тривалість, дата, нотатки). Журнал польоту обов'язково
пов'язаний з пілотом, а дрон у ньому вказується за бажанням.

## Стек

Java 17, Spring Boot 4, Spring Data JPA, Hibernate, MySQL, Liquibase, MapStruct, Lombok,
Spring Security (OAuth2 Client і Resource Server), Keycloak 24, Thymeleaf, Docker Compose.

## Запуск

Потрібен MySQL на `localhost:3306` з користувачем `root` і паролем `root`. База `fpv_fleet`
створюється автоматично.

Спочатку запускається Keycloak, realm `fpv-fleet` імпортується сам:

```
docker compose up -d
```

Адмінка Keycloak доступна на http://localhost:8081 (логін і пароль `admin`).
Після цього запускається застосунок (потрібен JDK 17 або новіший):

```
./mvnw spring-boot:run
```

Інтерфейс відкривається на http://localhost:8080.

У Keycloak створено трьох користувачів:

| Логін    | Пароль   | Ролі         |
|----------|----------|--------------|
| `admin`  | `admin`  | ADMIN, PILOT |
| `pilot`  | `pilot`  | PILOT        |
| `viewer` | `viewer` | немає        |

## Лабораторна робота №1

**Тема:** Spring Security.

**Мета:** закласти технічний фундамент системи, тобто обрати предметну область, зробити базовий CRUD,
поставити базу даних під контроль міграцій, додати простий UI та налаштувати подвійну модель
автентифікації: OIDC для користувачів інтерфейсу і JWT для прямих запитів до API.

### Базовий CRUD

Для кожної з чотирьох сутностей реалізовано стандартні шари: Entity, Repository, Service
і RestController. Між сутностями та DTO дані перетворюються через MapStruct. Кожен мапер має методи
`toDto`, `toEntity` і `updateEntity`, останній використовується під час оновлення запису.

API доступне за адресами `/api/v1/pilots`, `/api/v1/drones`, `/api/v1/equipment` та
`/api/v1/flight-logs`. Для кожного ресурсу є отримання списку і запису за ID, створення (POST),
оновлення (PUT) і видалення (DELETE). Для дронів і обладнання також можна отримати записи
конкретного пілота через `/pilot/{pilotId}`.

Сервіси самі завантажують пов'язаного пілота і дрон з репозиторіїв, тому неіснуючий `pilotId`
або `droneId` дає зрозумілу відповідь 404 замість помилки бази даних. `GlobalExceptionHandler`
повертає всі помилки в одному форматі: 404, якщо запис не знайдено, 400 для некоректних даних,
409 при порушенні цілісності і 403 при нестачі прав.

### Міграції бази даних

Схема бази створюється лише через Liquibase, а Hibernate працює в режимі `ddl-auto: validate`
і нічого в схемі не змінює. Головний changelog лежить у
`src/main/resources/db/changelog/db.changelog-master.xml` і підключає два changeset'и.

Перший (`v1-init-schema.xml`) створює таблиці `pilots`, `drones`, `equipment`, `flight_logs`
та зовнішні ключі між ними. Другий (`v2-flight-log-drone-set-null.xml`) змінює зовнішній ключ
`flight_logs.drone_id` на `ON DELETE SET NULL`, щоб після видалення дрона журнали польотів
зберігалися. На чистій базі обидва changeset'и застосовуються автоматично під час старту застосунку.

### Інтерфейс користувача

Інтерфейс зроблено на Thymeleaf (пакет `ui`, шаблони в `src/main/resources/templates`).
Головна сторінка `/` відкривається без входу. Після входу доступна панель `/ui`, де видно
користувача, його ролі та права. Сторінки `/ui/pilots`, `/ui/drones`, `/ui/equipment` і
`/ui/flight-logs` дозволяють переглядати, створювати, редагувати й видаляти записи.

UI працює через ті самі сервіси, що й REST API, тому обмеження `@PreAuthorize` діють і тут.
Якщо прав не вистачає, показується сторінка 403, а помилки бізнес-логіки виводяться
повідомленням над формою.

### Keycloak

Realm `fpv-fleet` описано у файлі `keycloak/fpv-fleet-realm.json`, він імпортується під час
старту контейнера. У realm є ролі `ADMIN` і `PILOT` та два клієнти. Клієнт `fpv-ui` (confidential,
authorization code flow) використовується для входу через інтерфейс. Клієнт `fpv-cli` (public,
password grant) потрібен, щоб отримувати JWT у curl, Postman або HTTP-клієнті IntelliJ.
Mapper `realm-roles` додає ролі користувача в claim `roles` у ID token, access token і userinfo.

### Подвійна автентифікація

У `SecurityConfig` налаштовано два незалежні `SecurityFilterChain`.

Перший ланцюг обробляє все, що починається з `/api/**`. Він працює без сесії, CSRF у ньому
вимкнено, а автентифікація відбувається лише через JWT у заголовку `Authorization: Bearer <token>`.
Токен перевіряється за `issuer-uri` Keycloak. Запит без токена або з невалідним токеном
отримує 401.

Другий ланцюг обробляє решту адрес, тобто інтерфейс. Неавтентифікованого користувача, який
відкриває `/ui`, перенаправляє на сторінку входу Keycloak. Після входу він повертається в застосунок
з дійсною сесією. При виході виконується RP-initiated logout, тож сесія завершується і в застосунку,
і в Keycloak.

В обох випадках claim `roles` перетворюється на authorities з префіксом `ROLE_`. Для API це робить
`JwtAuthenticationConverter`, для інтерфейсу власний `OidcUserService`.

### Обмеження доступу

Доступ обмежено на двох рівнях, які працюють незалежно один від одного.

На рівні `SecurityFilterChain` в API-ланцюгу будь-який DELETE-запит до `/api/**` і будь-яке
створення чи зміна пілотів дозволені тільки ролі `ADMIN`. Читання та інші запити доступні
будь-якому автентифікованому користувачу.

На рівні методів (`@EnableMethodSecurity`) кожен метод сервісу має анотацію `@PreAuthorize`.
Читати дані, а також створювати й змінювати дрони, обладнання та журнали можуть ролі `ADMIN`
і `PILOT`. Керувати пілотами і видаляти будь-які записи може лише `ADMIN`.

Незалежність цих рівнів добре видно на користувачі `viewer`. Він автентифікований, тому
`SecurityFilterChain` пропускає запит `GET /api/v1/drones`. Проте метод сервісу вимагає роль
`ADMIN` або `PILOT`, кидає `AccessDeniedException`, і клієнт отримує 403.

### Колекція HTTP-запитів

Для захисту підготовлено файл `http/fpv-fleet.http` для HTTP-клієнта IntelliJ з оточенням `dev`
(`http/http-client.env.json`). Файл запускається цілком і проходить весь сценарій по черзі.
Токени та ідентифікатори створених записів передаються між запитами автоматично, а кожен запит
перевіряє очікуваний код відповіді.

Спочатку отримуються токени для `admin`, `pilot` і `viewer`. Далі перевіряється, що запит
без токена і з невалідним токеном дає 401. Потім виконується повний CRUD для пілотів, дронів,
обладнання та журналів. Після цього `pilot` намагається створити пілота і видалити дрон та
отримує 403 від `SecurityFilterChain`, а `viewer` намагається прочитати дрони і створити журнал
та отримує 403 від `@PreAuthorize`. Наприкінці перевіряються відповіді 404 і видаляються всі
створені записи, причому журнал після видалення дрона залишається з `droneId = null`.

### Відповідність критеріям прийнятності

AC1 (CRUD і MapStruct) реалізовано в пакетах `controller`, `service` і `mapper`, перевіряється
CRUD-запитами колекції.

AC2 (міграції) забезпечують changelog'и в `db/changelog` разом із режимом `validate`. Перевірка:
старт на порожній базі і таблиця `DATABASECHANGELOG`.

AC3 (UI) реалізовано в пакеті `ui` і шаблонах, перевіряється на http://localhost:8080/ui.

AC4 (OIDC) налаштовано в `SecurityConfig#uiSecurityFilterChain`. Перевірка: відкрити `/ui`,
увійти в Keycloak і повернутися в застосунок.

AC5 (JWT) налаштовано в `SecurityConfig#apiSecurityFilterChain`, перевіряється запитами
з токенами і без них.

AC6 (403 від `SecurityFilterChain`) забезпечують правила `hasRole("ADMIN")` в API-ланцюгу,
перевіряється запитами від імені `pilot`.

AC7 (403 від `@PreAuthorize`) забезпечують анотації в сервісах, перевіряється запитами від імені
`viewer` або входом у UI як `viewer`.

AC8 (колекція запитів) знаходиться в `http/fpv-fleet.http`.

### Демонстрація на захисті

1. Запустити `docker compose up -d`, потім `./mvnw spring-boot:run`.
2. Відкрити http://localhost:8080/ui і переконатися, що відбувається перехід на логін Keycloak.
3. Увійти як `admin`. Після повернення в застосунок у шапці видно ролі `ADMIN` і `PILOT`.
   Створити, змінити і видалити кілька записів.
4. Вийти, увійти як `viewer` і відкрити сторінку дронів. З'являється сторінка 403 від `@PreAuthorize`.
5. Запустити `http/fpv-fleet.http` цілком і показати, що всі перевірки пройшли.

### Висновок

У першій лабораторній роботі створено основу семестрового проєкту. Зроблено REST API з повним
CRUD на стандартному стеку Spring Boot, схему бази під керуванням Liquibase і простий інтерфейс.
Spring Security налаштовано з двома паралельними способами автентифікації через Keycloak:
OIDC із сесією для браузера та JWT без сесії для API. Обмеження доступу показано на двох
незалежних рівнях, через правила адрес у `SecurityFilterChain` і через `@PreAuthorize`
на методах сервісів.
